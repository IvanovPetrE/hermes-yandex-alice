# Конфигурация

Секреты — только в `.env` Hermes (`~/.hermes/.env`), не в `config.yaml` и не в git. Плагин читает их через
`get_scoped_secret`, а не из окружения процесса.

## Переменные (`~/.hermes/.env`)

| Переменная | Обязательна | Назначение |
|---|---|---|
| `ALICE_PATH_SECRET` | да | Секретная часть пути webhook (64 hex-символа: `openssl rand -hex 32`). Плагин сверяет с ней весь путь запроса. |
| `ALICE_SKILL_ID` | да | ID навыка в Диалогах. Запросы с чужим `skill_id` получают отказ. |
| `ALICE_OWNER_USER_ID` | нет | `session.user.user_id` владельца. Пусто — режим привязки: все запросы получают «навык ещё не привязан». |
| `ALICE_TELEGRAM_CHAT` | нет | Чат Telegram для подробностей, внеходовых ответов, cron из голоса и карточек подтверждений. Бот — `TELEGRAM_BOT_TOKEN` той же области. Не задан — Telegram и подтверждения выключены. |
| `ALICE_TELEGRAM_OWNER_ID` | нет | Telegram user id владельца: кто нажимает карточки подтверждений. Пусто — id личного чата `ALICE_TELEGRAM_CHAT`; для группы без этой переменной подтверждения отключены. |

Значения этих переменных нигде не печатаются; в логах — только имена и исходы.

### Области (профили)

Адаптер живёт в процессе шлюза и принимает запросы в области **главного профиля** (`~/.hermes`), поэтому
`ALICE_PATH_SECRET`, `ALICE_SKILL_ID`, `ALICE_OWNER_USER_ID`, `ALICE_TELEGRAM_CHAT`, `ALICE_TELEGRAM_OWNER_ID` и
`TELEGRAM_BOT_TOKEN` должны быть в `~/.hermes/.env`. Если реплики идут в другой профиль (маршрутом ниже), то
`ALICE_TELEGRAM_CHAT` нужен и в `.env` целевого профиля (хук cron читает его там). Мультиплекс-шлюз при старте пишет
предупреждение «Profile '…': skipping platform 'yandex_alice'» для профилей без `ALICE_PATH_SECRET` — это норма.

## `config.yaml`

```yaml
plugins:
  enabled:
    - yandex-alice

platforms:
  yandex_alice:
    enabled: true
    extra:
      port: 8789          # обязателен; слушается только 127.0.0.1

gateway:
  multiplex_profiles: true
  profile_routes:
    - name: alice-profile
      platform: yandex_alice
      profile: voice-profile   # профиль, в чьей сессии идёт беседа
```

Для профиля, куда идут реплики:

```yaml
plugins:
  enabled:
    - yandex-alice
platform_toolsets:
  yandex_alice:
    - …    # набор как у вашего Telegram-профиля; `clarify` НЕ включать
```

`clarify` из голосового набора нужно исключить: агент не может переспросить голосом, а запрос ждал бы ответа в никуда.
`cronjob` допустим: хук `cron_guard` подставит доставку в `telegram:<ALICE_TELEGRAM_CHAT>` для задач, созданных голосом.

### Раскладка плагина

- **A2 (используется).** Один каталог `~/.hermes/plugins/yandex-alice`, симлинк на него из
  `~/.hermes/profiles/<профиль>/plugins/yandex-alice`, `plugins.enabled` в config главного и целевого профиля.
- **Голос в профиле по умолчанию.** Симлинк и второй `plugins.enabled` не нужны.
- **A3.** Только `platform_hints` без хука `cron_guard`: проще, но доставку задач cron, созданных голосом,
  придётся задавать явно. Этот вариант не проверялся.

## Home channel

В Hermes у платформы может быть «домашний чат» (`/sethome`, переменная `<ПЛАТФОРМА>_HOME_CHANNEL` или
`home_channel` в конфиге). Он нужен для cron с `deliver=<платформа>`, уведомлений о перезапуске шлюза и передачи
сессии. У голосового навыка такого чата нет: Алиса не умеет писать первой.

**Плагин не использует home channel, и задавать его для `yandex_alice` не нужно.** Следствия:

- В первой реплике каждой новой беседы Hermes отправляет служебное «No home channel is set for Yandex_Alice…».
  Плагин это сообщение не озвучивает и не пересылает: оно приходит внутри хода без метки итога и отсекается правилом
  `sends.py`.
- Cron, созданный голосом, получает доставку в `telegram:<ALICE_TELEGRAM_CHAT>` от хука `cron_guard`
  (поэтому `ALICE_TELEGRAM_CHAT` нужен в `.env` целевого профиля).
- Всё, что агент или шлюз отправляет вне хода, плагин сам пересылает в Telegram с подписью «Алиса:».
- Потерянный перезапуском вопрос плагин не «дозапускает»: следующая реплика получает «Вопрос потерялся, повторите».

Если всё же задать home channel для `yandex_alice`, служебное сообщение пропадёт, но cron и уведомления шлюза начнут
уходить в платформу без чата; на практике это тот же Telegram, только с лишним шумом. Не проверялось.

## Параметры, не вынесенные в конфиг

Эти значения заданы в коде (`dialog.py`, `engine.py`, `protocol.py`) и не настраиваются:

| Параметр | Значение |
|---|---|
| Бюджет удержания запроса | 3,5 с (лимит Алисы около 4,5 с) |
| Тело запроса | до 16 КиБ, чтение до 5 с |
| Текст реплики | до 1000 символов |
| Голос в одной реплике | до 900 символов (лимит Алисы 1024), длиннее — по частям |
| Частота | 6 команд в минуту |
| Продолжение беседы | если с последней реплики владельца меньше 2 часов |
| Хранение незабранного ответа | 24 часа |
| «Вопрос потерялся» | через 10 минут после старта шлюза без итога |
| Очередь Telegram | срок отправки 60 с, один повтор |

## Предупреждения

- **Уровень логов DEBUG.** При DEBUG библиотека Telegram пишет в лог текст сообщений, то есть подробности ответа
  агента. Держите уровень INFO и выше, если логи хранятся вне вашего контроля.
- **Логи прокси.** Секретный путь — это доступ к навыку. Прокси не должен писать полный URI запроса в общий лог
  ([Caddy-пример](deployment.md)).
- **Telegram-чат группа.** Для группы задайте `ALICE_TELEGRAM_OWNER_ID`, иначе карточки подтверждений не работают.
- **Подтверждения — только в Telegram.** Команда, требующая подтверждения, ждёт нажатия карточки в чате; если
  карточка не дошла или подтверждения не настроены, команда не выполняется, Алиса говорит об этом.
