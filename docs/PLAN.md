# План: плагин «Яндекс Алиса» для Hermes Agent

Статус: утверждаемый план, 2026-11-14. Факты и обоснования — `docs/RECON.md`.
Репозиторий публикуется на GitHub: всё, что в git, пишется как для чужого читателя (см. «Публикация»).

## 1. Что строим

Плагин Hermes вида `kind: platform`: Яндекс Алиса становится ещё одним каналом шлюза.

```
Алиса → HTTPS-прокси (Caddy) → 127.0.0.1:<порт> в процессе шлюза (AliceAdapter)
      → handle_message(MessageEvent) → сессия шлюза нужного профиля → AliceAdapter.send()
      ├→ голосовой ответ в текущий или следующий запрос Алисы
      └→ подробный ответ в настроенный чат Telegram (штатный отправитель Hermes)
```

Принятые решения (приоритет над ТЗ и планом v3):
1. **Диалог.** После ответа сессия Алисы остаётся открытой; реплики продолжают одну беседу Hermes.
   Закрытие — «хватит/стоп/выход» или таймаут Алисы.
2. **История — в Hermes** (сессия шлюза, `state.db`). Плагин хранит текущую беседу, вопрос в работе,
   незабранный ответ и статус доставки.
3. **Беседа принадлежит владельцу, а не сессии Алисы** — подробно `docs/RECON.md`, «Модель беседы»:
   быстрый ответ сразу; иначе «Вопрос принят. Спросите ответ позже или готовы подождать?»; ожидание —
   как в нынешнем bridge; «скинь ответ» — в той же или новой сессии; другая фраза при незабранном
   ответе — «Начать новый диалог или продолжить прошлый?».
4. **Один вопрос в работе на беседу**; новая фраза во время ожидания не запускается молча.
5. **Telegram — по необходимости:** длинный ответ, подробности, «пришли в Телеграм», незабранный ответ
   при переходе в новый диалог.
6. **Подтверждения опасных действий — только в Telegram**; до проверки — отклонять. «Да» голосом
   никогда не разрешение.
7. **Только публичный API Hermes** (`plugins/public-api.md`), без правок ядра, без внутренних HTTP-вызовов
   (Chat Completions, webhook) и без отдельного контейнера.
8. Профиль, чат Telegram и параметры — из настроек, никогда из входного текста.
9. **Команды голосом — через интенты Яндекс Диалогов** (свои интенты навыка + встроенные `YANDEX.*`),
   как в нынешнем bridge; грамматики интентов — в репозитории.

Вне первой версии: общая история Алисы и Telegram, поддержка многих версий Hermes, многопользовательский
режим, публикация в каталоге плагинов Hermes.

### Этап 1. Прототипы (проверка реализуемости)

Сначала чтение кода установленной версии Hermes, затем минимальный эксперимент во временном
`HERMES_HOME` с синтетическими ID и секретами (на сервере — с согласия). Каждый прототип — вердикт
VALIDATED / PARTIAL / INVALIDATED с командами и ограничениями, запись в `docs/RECON.md`.
Если нужного публичного интерфейса нет — фиксируем блокер и решаем отдельно; скрытых обходов нет.

- **S1. Финальность и привязка ответа** (главный риск). **PARTIAL, 2026-11-14** (`docs/RECON.md`,
  «S1»; проба `prototypes/s1/`, запуск вручную): конец хода — хук `on_processing_complete`; итог —
  `reply_to == message_id` + `notify` (метки LINE — только подсказка); ошибка агента приходит обычным
  итогом с `success`; вторая фраза в занятую беседу ломает привязку в обоих режимах — гейт Р2 обязателен.
- **S2. Профиль.** **PARTIAL, 2026-11-14** (`docs/RECON.md`, «S2»; проба `prototypes/s2/`): адаптер,
  `platforms.yandex_alice` и `ALICE_*` — в профиле по умолчанию, маршрут без `user_id` переносит ход,
  сессию, историю и `platform_toolsets` в целевой профиль; подсказка и уровень плагина туда сами не
  доходят (плагин ещё и в каталоге профиля или `platform_hints`/`display.platforms` — решение владельца);
  адаптеру нужен `validate_config` по секрету области; `allowlist_suppresses_pairing` код привязки при
  маршруте не гасит — `unauthorized_dm_behavior: ignore` гасит; **решено 2026-11-16: второго рубежа не ставим**
  (только проверка адаптера, код привязки при её пропуске — принятый риск).
- **S3. Telegram.** **PARTIAL, 2026-11-15** (`docs/RECON.md`, «S3»; проба `prototypes/s3/`):
  `standalone_sender_fn` работает из плагина в loop через публичный API, но только со своим `PlatformConfig`
  из `connect()` (токен бота профиля по умолчанию; без токена — исключение или чужой бот) и отправкой в
  контексте `connect()` (иначе прокси и уведомления — профиля хода); `dict` не отличает отказ от «возможно
  дошло», Hermes сам повторяет 5xx/429, длинный текст может дойти частично; первый `get("telegram")` — до 0,9 с
  синхронно.
- **S4. Подтверждения.** **PARTIAL, 2026-11-15** (`docs/RECON.md`, «S4»; проба `prototypes/s4/`): все
  сценарии зелёные — переопределённый `_send_exec_approval_prompt` шлёт свою карточку ботом профиля по
  умолчанию (`Application.bot` из `register_platform_handler`, у чужого бота фабрика не вызывается), своё
  нажатие `^hya:` → `resolve_gateway_approval_card` без `actor_id`; нажимает только владелец в своём чате;
  ошибка, срок 10 с или отключённые подтверждения → сразу `resolve_gateway_approval(deny, reason, request_id)`.
  PARTIAL: правка карточки на таймауте, блок полной команды и текст `/approve` держатся на недокументированном
  поведении; агент при отказе плагина видит «denied by user».
- **S5. Жизненный цикл.** **PARTIAL, 2026-11-16** (`docs/RECON.md`, «S5»; проба `prototypes/s5/`, контроль из
  `17ebebb`: A 18, B 6, C 7, D 3 — OK): импорт порта не открывает; connect/reload/переподключение/остановка/`SIGKILL`
  оставляют один listener (reload импортирует модуль заново, адаптер прежний — состояние не в глобальных
  переменных модуля); занятый порт — retryable `bind_failed`, шлюз и другие платформы живы, повтор шлюзом
  бесконечный, circuit breaker нет; перезапуск посреди хода — Hermes сам дозапускает внутренний ход
  (`internal`, `message_id=None`, итог с `reply_to=None` и `notify=True`; нужен `interactive_resume=False`) или
  досылает ответ из леджера с пометкой «♻️ …:» вне хода (срез по форме); без пометки и текст ошибки вне хода
  по метаданным неотличимы. PARTIAL: опора на неописанное в руководстве (`internal`, `interactive_resume`,
  `_set_fatal_error`/`_notify_fatal_error`); поправка к М6 принята.
- **S6. Сессия и cron.** **PARTIAL, 2026-11-16** (`docs/RECON.md`, «S6»; проба `prototypes/s6/`, контроль из
  `7349c33`: A 28, B 7, C 3 — OK): ключ `agent:<профиль>:yandex_alice:dm:<chat_id>` стабилен, история — сессия шлюза,
  сжатие идёт на месте (id тот же); cron без `deliver` из голоса → `origin` → `delivery_failed`, до адаптера не доходит;
  `telegram:<чат>` доходит только для чата с маршрутом в целевой профиль; страховка — хук `pre_tool_call`
  (`cron_guard`), работает только при плагине и `ALICE_TELEGRAM_CHAT` в целевом профиле (A2 — решение владельца);
  без `clarify` встречный вопрос — обычный итог; внеходовое → Telegram «Алиса:». PARTIAL: опора на A2,
  `SharedRouteAdapters`, сжатие на месте; хук в рабочем процессе шлюза не проверен.

Готово, когда: S1–S6 с вердиктами, план обновлён по выводам до написания адаптера.

### Этап 2. Протокол и модель диалога (`yandex-alice/protocol.py`, `yandex-alice/dialog.py`)

Чистая логика без импортов Hermes, полностью покрыта unit-тестами.
- Переделать перенесённый `protocol.py`: `end_session=False` по умолчанию, тексты под диалог.
- Машина состояний «Модели беседы» (`docs/RECON.md`): «да/нет» — по последней озвученной реплике
  (предложение ждать / «новый или прошлый?»); реплика без интента на «подождёте?» — ждём, на «новый
  или прошлый?» — переспросить; после забранного ответа всё уходит агенту (М4–М6).
- Повтор того же HTTP-хода Алисы (тот же `session_id` + `message_id`) получает прежний ответ.
- Формат ответа агента (голос/Telegram) — через `platform_hint`, разбор с безопасным fallback (по Р3).
- Итог-ошибка шлюза (**решено 2026-11-16**, S1): чистая функция узнаёт известные формы текста ошибки Hermes (пустой
  ответ модели, сбой провайдера; формы закрепляются тестом совместимости, этап 6) → «не получилось, попробуйте ещё
  раз», исходный текст — в Telegram «Алиса:»; не узнали — озвучивается как ответ.
- Отказ при недоставленной карточке (**решено 2026-11-16**, S4): карточка хода с меткой `failed` → озвучивается свой
  текст («запрос на подтверждение не дошёл до Телеграма, команда не выполнена»), ответ агента — в Telegram.
- Отправки вне хода (**решено 2026-11-16, S6**): не служебная и не восстановленная → Telegram с подписью «Алиса:»,
  не озвучивается (`recovery.forward_text` из `prototypes/s6/plugin/`); итог внутреннего хода озвучивается как
  незабранный ответ только при «вопросе в работе» без итога, иначе — Telegram «Алиса:» (результат `run`, фон,
  делегирование). Тексты — этап 2.

### Этап 3. Адаптер и HTTP-вход (`yandex-alice/adapter.py`, `yandex-alice/__init__.py`)

- `register(ctx)` → `ctx.register_platform(...)`; лёгкий импорт, listener только в `connect()`; `validate_config` по
  секрету (S2); `disconnect()` — `site.stop` + `runner.cleanup`, `AppRunner(access_log=None)` (S5). Занятый порт —
  `_set_fatal_error("bind_failed", …, retryable=True)` без пути и исключения в тексте, и `interactive_resume = False`:
  оба — недокументированные члены `base`; **решено 2026-11-16 (S5): опираемся** на них и на `on_processing_*`,
  каждый закрепляется тестом совместимости (этап 6) и проверкой после `hermes update` (`docs/compatibility.md`).
- `aiohttp`, только loopback; ограничения тела, заголовков, соединений; общий срок ответа
  (бюджет ~3,5 с при лимите Алисы 4,5 с) по монотонным часам.
- Проверки по порядку: секретный путь (constant-time) → формат → `ping` → `skill_id` → владелец →
  лимит частоты. `MessageEvent.allow_gateway_control=False`. Секреты — `get_scoped_secret`, не `os.environ`.
- `send()` по правилу S1: итог — отправка с `reply_to == message_id` открытого хода, `notify is True` и
  без `_interim_send` (префиксы `⚡ ⏳ ⏩ 💾` итог не отменяют), кладётся
  в кэш хода; конец хода — `on_processing_start`/`on_processing_complete`; прочие отправки не озвучиваются.
  Пока ход беседы открыт, новая фраза в `handle_message` не передаётся (гейт Р2).
- Логи без пути, тела и текста реплик; диагностика только по метаданным.
- По S6 (`docs/RECON.md`, «S6» → «Выводы»): `platform_hint` — правило `deliver=telegram:<чат>` для cron;
  хук `pre_tool_call` на `cronjob_manage` по `cron_guard.guard_args` (перенос из `prototypes/s6/plugin/` с
  `GuardTests`) — **условно: только при раскладке A2, выбор A2/A3 — решение владельца**; инвариант хука — никогда не
  бросает, сразу выходит для чужих инструментов и не-голосовых сессий; `provides_hooks: [pre_tool_call]` в
  манифесте. В `platform_toolsets.yandex_alice` целевого профиля — `cronjob`, без `clarify` (`docs/configuration.md`).

### Этап 4. Хранилище (`yandex-alice/storage.py`)

SQLite в каталоге данных плагина (`plugins.plugin_storage`): неозвученный ответ хода, статус доставки
в Telegram, дедупликация ходов Алисы. Неозвученный ответ выдаётся при следующем входе владельца, в том
числе в новой сессии и после перезапуска шлюза. Неясный исход хода или отправки автоматически не
повторяется. Срок хранения ограничен; тексты — персональные данные.

По S5 (`docs/RECON.md`, «S5» → «Выводы»): ответ, который Hermes продолжил или дослал после перезапуска,
записывается как обычный незабранный (внутренний ход: `event.internal`, `message_id=None`; леджер: отправка вне
хода, пометка «♻️ …:» срезается по форме); первый из двух внутренних ходов пустой — завершение внутреннего хода
без итога вопрос не закрывает, закрывает итог или таймаут; хранилище помнит «вопрос в работе» — это лишь сужает
круг внеходовых кандидатов в ответ, но не отличает текст ошибки от ответа (вопрос владельцу, `docs/RECON.md`,
«S5»); состояние — не в глобальных переменных модуля (reload импортирует модуль заново).

По S6: внутренний ход без «вопроса в работе» (результат `run`, фоновой задачи, делегирования — `internal=True`,
`message_id=None`, как автопродолжение) незабранным ответом не становится — его итог уходит в Telegram «Алиса:»;
различие — только по состоянию хранилища (решение владельца, `docs/RECON.md`, «S6»).

Задел сценариев (из параллельной незапущенной пробы S6 в соседнем ворктри; это **гипотезы для проверки**, не
наблюдения — на этапе 4/6 проверить в тестах `storage.py` и на стенде этапа 8):
- Сбои доставки в Telegram (cron/внеходовое): 403, зависший ответ, «принято, но подтверждение потеряно»
  (клиенту неотличимо от зависания) — терминальная доставка не повторяется ни вторым drain, ни после перезапуска
  шлюза; статус в `storage.py` хранит исход и не обещает exactly-once.
- Cron во время активного голосового хода: результат не должен попасть в итог хода и не закрывать его.
- Cron в старую беседу после смены `chat_id` («новый диалог» = новый `chat_id`): доставка идёт в Telegram, историю
  новой беседы не трогает; согласовать с М1–М6.
- История при `mirror_delivery` / `attach_to_session` (true/false) и `in_channel`: попадает ли результат cron в
  контекст следующего голосового хода и в Telegram-сессию; выбрать настройку, при которой голосовая беседа
  не засоряется.
- Проба соседа запрещала сеть вне loopback (Python DNS/connect) и убирала процессы по PID ребёнка, не по argv —
  перенять в обвязку стенда.

### Этап 5. Telegram и подтверждения

По выводам S3/S4/S6: доставка подробного ответа, честная ошибка при сбое; подтверждения в Telegram
одноразовые, с проверкой нажавшего; cron с явным адресом доставки — `telegram:<ALICE_TELEGRAM_CHAT>`, и этот чат
обязан быть в маршруте `gateway.profile_routes` (`platform: telegram`, `chat_id`) в целевой профиль, иначе cron
целевого профиля без своего бота в него не доставит (S6, C3). Пересылка внеходового — тем же отправителем S3.

Доставка (S3, `docs/RECON.md`, «S3» → «Выводы»):
- в `connect()`: свой `PlatformConfig` — `token` из `get_scoped_secret("TELEGRAM_BOT_TOKEN")`, чат из
  `ALICE_TELEGRAM_CHAT`, `extra` — белый список ключей `telegram_*` из `platforms.yandex_alice.extra`;
  отправитель из реестра (первый `get()` — вне loop); снимок контекста. Нет токена или чата — доставка
  отключена, отправитель не вызывается;
- отправка — фоновой задачей в копии контекста `connect()`, вне бюджета ответа Алисе; `notify=True`;
  общий срок 60 с;
- итог — `delivered` / `failed` / `uncertain`, в хранилище (этап 4); автоматических повторов нет;
  озвучка и показ `failed`/`uncertain` и частичной доставки длинного текста — решение владельца (этап 2/5).

Подтверждения (S4, `docs/RECON.md`, «S4» → «Выводы»):
- `_send_exec_approval_prompt` → своя карточка (только `once`/`deny`; «Разрешить» — только если команда видна
  целиком) → `Application.bot` профиля по умолчанию (фабрика `register_platform_handler`, дом и токен своей
  области) → обработчик `^hya:` → `resolve_gateway_approval_card` без `actor_id`;
- владелец — `ALICE_TELEGRAM_OWNER_ID` (новая настройка; в манифест — на этапе 3), иначе id лички
  `ALICE_TELEGRAM_CHAT`; группа без настройки — подтверждения отключены; нажатие — только в этом чате;
- срок отправки 10 с; сбой → отказ с причиной по `request_id`, метка `failed`; поздняя карточка — «неактуален»;
- книга карточек и `BookTests` переносятся из `prototypes/s4/` в `yandex-alice/` и `tests/` с доработками из
  ревью (`docs/RECON.md`, «S4» → «Выводы», п. 10: отмена хода, переподключение, бюджет длины, гонка правки,
  ссылки на задачи);
- в логи — только длины, `request_id` и исход, без текста команды и причины.

### Этап 6. Тесты

- Unit (без Hermes): протокол, диалог, хранилище, HTTP-обработчик на настоящем loopback.
- Совместимость: тесты адаптера против checkout Hermes на закреплённой ревизии (в CI — клонировать
  ревизию из `docs/compatibility.md`); пропущенный тест не считается пройденным. Сюда переносятся
  закреплённые S1 случаи (итог по `reply_to`+`notify`, хук после итога, исключения занятой сессии);
  `prototypes/s1/` до этого запускается только вручную.
- Сценарии lifecycle и негативные HTTP-тесты — по мотивам `alice-voice` (с уведомлением об авторстве).
- Живая приёмка на стенде (раздел 4) — вручную, результаты в отчёт без персональных данных.

  отслеживается. Найденное в истории — переписать историю до первой публикации.
