# План: плагин «Яндекс Алиса» для Hermes Agent

Статус: утверждаемый план, 2026-11-14. Факты и обоснования — `docs/RECON.md`.
Репозиторий публикуется на GitHub: всё, что в git, пишется как для чужого читателя (см. «Публикация»).

## 1. Что строим

Плагин Hermes вида `kind: platform`: Яндекс Алиса становится ещё одним каналом шлюза.

```
Алиса → HTTPS-прокси (Caddy) → 127.0.0.1:<порт> в процессе шлюза (AliceAdapter)
      → handle_message(MessageEvent) → сессия шлюза нужного профиля → AliceAdapter.send()
      ├→ голосовой ответ в текущий или следующий запрос Алисы
      └→ подробный ответ в настроенный чат Telegram (штатный отправитель Hermes)
```

Принятые решения (приоритет над ТЗ и планом v3):
1. **Диалог.** После ответа сессия Алисы остаётся открытой; реплики продолжают одну беседу Hermes.
   Закрытие — «хватит/стоп/выход» или таймаут Алисы.
2. **История — в Hermes** (сессия шлюза, `state.db`). Плагин хранит текущую беседу, вопрос в работе,
   незабранный ответ и статус доставки.
3. **Беседа принадлежит владельцу, а не сессии Алисы** — подробно `docs/RECON.md`, «Модель беседы»:
   быстрый ответ сразу; иначе «Вопрос принят. Спросите ответ позже или готовы подождать?»; ожидание —
   как в нынешнем bridge; «скинь ответ» — в той же или новой сессии; другая фраза при незабранном
   ответе — «Начать новый диалог или продолжить прошлый?».
4. **Один вопрос в работе на беседу**; новая фраза во время ожидания не запускается молча.
5. **Telegram — по необходимости:** длинный ответ, подробности, «пришли в Телеграм», незабранный ответ
   при переходе в новый диалог.
6. **Подтверждения опасных действий — только в Telegram**; до проверки — отклонять. «Да» голосом
   никогда не разрешение.
7. **Только публичный API Hermes** (`plugins/public-api.md`), без правок ядра, без внутренних HTTP-вызовов
   (Chat Completions, webhook) и без отдельного контейнера.
8. Профиль, чат Telegram и параметры — из настроек, никогда из входного текста.
9. **Команды голосом — через интенты Яндекс Диалогов** (свои интенты навыка + встроенные `YANDEX.*`),
   как в нынешнем bridge; грамматики интентов — в репозитории.

Вне первой версии: общая история Алисы и Telegram, поддержка многих версий Hermes, многопользовательский
режим, публикация в каталоге плагинов Hermes.

## 3. Этапы

Каждый этап заканчивается коммитом с зелёными тестами. Действия на сервере (стенд, установка,
перезапуск шлюза, переключение) — только с отдельного согласия владельца.

### Этап 0. Репозиторий, готовый к публикации

- Имя (Р4), `LICENSE` (MIT), `THIRD_PARTY_NOTICES.md` (для сценариев тестов из `alice-voice`, MIT).
- `.gitignore`: секреты, `CLAUDE.md`/`AGENTS.md`/`.claude/`, локальные настройки развёртывания.
- CI GitHub Actions: unit-тесты на версии Python, на которой работает Hermes.
- Автор коммитов — обезличенный (`<project> contributors`), без личной почты.
- Вычистить отслеживаемые файлы от привязок к нашему серверу (см. «Публикация»).
- Первый коммит.

### Этап 1. Прототипы (проверка реализуемости)

Сначала чтение кода установленной версии Hermes, затем минимальный эксперимент во временном
`HERMES_HOME` с синтетическими ID и секретами (на сервере — с согласия). Каждый прототип — вердикт
VALIDATED / PARTIAL / INVALIDATED с командами и ограничениями, запись в `docs/RECON.md`.
Если нужного публичного интерфейса нет — фиксируем блокер и решаем отдельно; скрытых обходов нет.

- **S1. Финальность и привязка ответа** (главный риск). **PARTIAL, 2026-11-14** (`docs/RECON.md`,
  «S1»; проба `prototypes/s1/`, запуск вручную): конец хода — хук `on_processing_complete`; итог —
  `reply_to == message_id` + `notify` (метки LINE — только подсказка); ошибка агента приходит обычным
  итогом с `success`; вторая фраза в занятую беседу ломает привязку в обоих режимах — гейт Р2 обязателен.
- **S2. Профиль.** `gateway.profile_routes {platform: yandex_alice, profile: …}` в мультиплексе;
  `platform_toolsets.yandex_alice`; где лежит плагин и какой профиль поднимает адаптер и порт.
- **S3. Telegram.** `platform_registry.get("telegram").standalone_sender_fn(pconfig, chat_id, text)`:
  какой токен виден в области целевого профиля, результат и ошибки, работа в event loop.
- **S4. Подтверждения.** Что делает базовый `send_exec_approval`; перенос карточки в Telegram:
  `ctx.register_platform_handler("telegram", …)` + `resolve_gateway_approval_card(..., actor_id=…)`.
  Если не выходит — первая версия отклоняет такие действия и говорит об этом.
- **S5. Жизненный цикл.** Импорт без порта; connect/disconnect/reload оставляют один listener;
  занятый порт; перезапуск с активным ходом.
- **S6. Сессия и cron.** Как шлюз хранит сессию плагинной платформы (ключ, история, сжатие);
  куда доставит cron, созданный из голосовой сессии, и как задать явный адрес.

Готово, когда: S1–S6 с вердиктами, план обновлён по выводам до написания адаптера.

### Этап 2. Протокол и модель диалога (`yandex-alice/protocol.py`, `yandex-alice/dialog.py`)

Чистая логика без импортов Hermes, полностью покрыта unit-тестами.
- Переделать перенесённый `protocol.py`: `end_session=False` по умолчанию, тексты под диалог.
- Машина состояний «Модели беседы» (`docs/RECON.md`): «да/нет» — по последней озвученной реплике
  (предложение ждать / «новый или прошлый?»); реплика без интента на «подождёте?» — ждём, на «новый
  или прошлый?» — переспросить; после забранного ответа всё уходит агенту (М4–М6).
- Повтор того же HTTP-хода Алисы (тот же `session_id` + `message_id`) получает прежний ответ.
- Формат ответа агента (голос/Telegram) — через `platform_hint`, разбор с безопасным fallback (по Р3).
- По S1 решить с владельцем: как озвучивать итог-ошибку шлюза (пустой ответ модели, сбой провайдера —
  англ. технический текст, по контракту неотличим от ответа) и что делать с отправками вне хода
  (текст ошибки после закрытия хода, повторная доставка, фоновые уведомления, cron).

### Этап 3. Адаптер и HTTP-вход (`yandex-alice/adapter.py`, `yandex-alice/__init__.py`)

- `register(ctx)` → `ctx.register_platform(...)`; лёгкий импорт, listener только в `connect()`.
- `aiohttp`, только loopback; ограничения тела, заголовков, соединений; общий срок ответа
  (бюджет ~3,5 с при лимите Алисы 4,5 с) по монотонным часам.
- Проверки по порядку: секретный путь (constant-time) → формат → `ping` → `skill_id` → владелец →
  лимит частоты. `MessageEvent.allow_gateway_control=False`. Секреты — `get_scoped_secret`, не `os.environ`.
- `send()` по правилу S1: итог — отправка с `reply_to == message_id` открытого хода, `notify is True` и
  без `_interim_send` (префиксы `⚡ ⏳ ⏩ 💾` итог не отменяют), кладётся
  в кэш хода; конец хода — `on_processing_start`/`on_processing_complete`; прочие отправки не озвучиваются.
  Пока ход беседы открыт, новая фраза в `handle_message` не передаётся (гейт Р2).
- Логи без пути, тела и текста реплик; диагностика только по метаданным.

### Этап 4. Хранилище (`yandex-alice/storage.py`)

SQLite в каталоге данных плагина (`plugins.plugin_storage`): неозвученный ответ хода, статус доставки
в Telegram, дедупликация ходов Алисы. Неозвученный ответ выдаётся при следующем входе владельца, в том
числе в новой сессии и после перезапуска шлюза. Неясный исход хода или отправки автоматически не
повторяется. Срок хранения ограничен; тексты — персональные данные.

### Этап 5. Telegram и подтверждения

По выводам S3/S4: доставка подробного ответа, честная ошибка при сбое; подтверждения в Telegram
одноразовые, с проверкой нажавшего; cron с явным адресом доставки.

### Этап 6. Тесты

- Unit (без Hermes): протокол, диалог, хранилище, HTTP-обработчик на настоящем loopback.
- Совместимость: тесты адаптера против checkout Hermes на закреплённой ревизии (в CI — клонировать
  ревизию из `docs/compatibility.md`); пропущенный тест не считается пройденным. Сюда переносятся
  закреплённые S1 случаи (итог по `reply_to`+`notify`, хук после итога, исключения занятой сессии);
  `prototypes/s1/` до этого запускается только вручную.
- Сценарии lifecycle и негативные HTTP-тесты — по мотивам `alice-voice` (с уведомлением об авторстве).
- Живая приёмка на стенде (раздел 4) — вручную, результаты в отчёт без персональных данных.

### Этап 7. Документация (для GitHub)

`README.md` (что это, установка, быстрый старт), `docs/configuration.md` (параметры и переменные,
секреты отдельно), `docs/yandex-dialogs.md` (навык, интенты и их грамматики), `docs/deployment.md`
(Caddy-пример с подавлением секретного пути в логах, `network_mode: host` для Docker),
`docs/compatibility.md` (проверенная версия Hermes), `docs/rollback.md`. Примеры — только с
плейсхолдерами (`example.org`, `<skill-id>`).

### Этап 8. Стенд, приёмка и переход (сервер, с согласия)

1. Паспорт стенда (раздел 4) заполнен и проверен.
2. Плагин на другом loopback-порту; синтетические запросы; старый bridge продолжает работать.
3. Приёмка по сценариям; известные ограничения записаны.
4. Переключение upstream Caddy на порт плагина; один исполнитель команд; smoke-тест голос + Telegram.
5. Старый контейнер остановлен, не удалён, на период наблюдения; затем уборка неиспользуемых
   маршрутов и секретов (API/webhook Hermes целиком не выключать без проверки других потребителей).
Откат: вернуть upstream Caddy, остановить плагин; неясные ходы не повторять.

### Этап 9. Публикация на GitHub (с согласия)

Проверка перед первым push (раздел 5), создание репозитория, push, проверка CI.

## 5. Публикация: правила для всего, что в git

- Нет секретов, реальных доменов, IP, chat_id, user_id, skill_id, имён пользователей и путей нашего
  сервера — только плейсхолдеры. Серверная специфика и журнал состояния — в `CLAUDE.md` (не в git).
- Никаких приватных материалов владельца (ТЗ, планы, логи); ссылаться на них только из `CLAUDE.md`.
- Код и документация не завязаны на имя профиля `voice-profile` и конкретный чат: всё задаётся настройками.
- Лицензия MIT; заимствования из `alice-voice` — с сохранением уведомления (`THIRD_PARTY_NOTICES.md`).
- Перед каждым push: unit-тесты, `hermes plugins validate` без private-import предупреждений, поиск
  по истории git на секреты и персональные ID (`git log -p` + шаблоны), проверка что `CLAUDE.md` не
  отслеживается. Найденное в истории — переписать историю до первой публикации.
- Публикация и каждый push в публичный репозиторий — отдельное согласие владельца.
