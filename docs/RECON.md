## Почему не `alice-voice`

`alice-voice` — плагин вида `standalone`, а не платформа:

- HTTP-сервер (`http.server`, поток) поднимается из `ctx.register_telegram_handler(...)` —
  только пока подключён Telegram; в режиме `plugins.isolation: host` не работает.
- Реплика уходит `ctx.inject_message(text, session_key="agent:main:telegram:dm:<id>")` в одну
  фиксированную личку **main**; вызов возвращает только «принято» — ответа агента плагин не видит,
  поэтому Алиса ничего не озвучивает. Профиль — только `default`.
- Стоит взять: строгая проверка тела, `hmac.compare_digest` для пути, отказ от слэш-команд и
  управляющих символов, полное молчание в логах (`log_message`/`handle_error` пустые).

## Целевая форма: `kind: platform`

Штатный путь для нового канала без правки ядра —
`website/docs/developer-guide/adding-platform-adapters.md`, «Plugin Path (Recommended)»:

```
Алиса → Caddy (TLS) → 127.0.0.1:<порт> в процессе шлюза (AliceAdapter.connect: aiohttp)
      → self.handle_message(MessageEvent) → сессия шлюза → AliceAdapter.send(chat_id, ответ)
```

`register(ctx)` → `ctx.register_platform(name="yandex_alice", adapter_factory=..., check_fn=..., platform_hint=...,
display_tier="minimal", max_message_length=..., allowed_users_env=...)`.

## Модель диалога (решение владельца 2026-11-14)

Логика старого bridge не сохраняется. Старая схема — одна команда на голосовую сессию: ответ
озвучивается и сессия закрывается (`end_session: true`), «Голосовая сессия не имеет памяти между
командами». Новая — **диалог**: после ответа сессия Алисы остаётся открытой, следующая реплика
продолжает ту же беседу Hermes с историей. Отсюда вопросы для проектирования:

- **Беседа Hermes ↔ сессия Алисы.** Естественно `chat_id` = `session.session_id` (новый запуск навыка —
  новая беседа). Альтернатива — `user_id` (одна длинная беседа на все запуски); тогда нужен сброс (`/new`).
- **Завершение.** Только по явному «хватит/стоп/выход» или по таймауту Алисы; закрытие сессии Алисой
  само по себе ничего у агента не отменяет.
- **Медленный ответ внутри диалога.** Удержание «Думаю…» остаётся, но реплику во время ожидания
  надо различать: согласие ждать, «пришли в Телеграм» или новая фраза в диалог. Для новой фразы
  шлюз умеет очередь, прерывание или подмешивание (`⚡ ⏳ ⏩`) — выбрать поведение.
- **Telegram.** Дублировать каждый ход или только длинные/«пришли в Телеграм» ответы — от этого
  зависит, нужен ли формат «ГОЛОС/ТЕЛЕГРАМ» в `platform_hint`.
- **Тексты ответов** («Скажите задачу…», «Ответ — в Телеграме.») пересматриваются под диалог.

### Принятые решения (2026-11-14)

1. **История диалога хранится в Hermes**, а не в памяти плагина или bridge: сессия шлюза целевого
   профиля, `state.db`. Собственного кэша истории (ходы/байты/TTL) не делаем — переживает
   перезапуск шлюза, агент видит в контексте и результаты инструментов, а не только текст.
2. **Сессия Алисы после ответа не закрывается** (`end_session: false`) — всегда, без маркера от агента.
   Закрытие — явное «хватит/стоп/выход» или таймаут Алисы.
3. ~~Два состояния `waiting`/`dialog` на сессию Алисы~~ — заменено «Моделью беседы» ниже.
4. **Один вопрос в работе на беседу.** Новая фраза во время ожидания не запускается молча —
   см. шаг 4 «Модели беседы».
5. «Да» в диалоге — подтверждение по смыслу для агента, но не обход шлюза подтверждений Hermes.

### Модель беседы (решение владельца 2026-11-14, уточнение)

Беседа — одна беседа Hermes с историей; принадлежит **владельцу, а не сессии Алисы**: переживает
закрытие навыка и новый запуск. Активная беседа одна. Идентификатор беседы выдаёт плагин и передаёт
шлюзу как `chat_id`; «новый диалог» — новый идентификатор (новая сессия Hermes без истории). Плагин
хранит в SQLite текущую беседу, вопрос в работе и готовый незабранный ответ.

Ожидание — **как в нынешнем bridge**, плюс возможность забрать ответ позже:

1. **Вопрос.** Агент успел за бюджет (~3,5 с) — Алиса сразу озвучивает ответ. Не успел —
   «Вопрос принят. Спросите ответ позже или готовы подождать?»
2. **Реплика на это предложение:**
   - «подожду»/«да» — удержание как сейчас: готово — озвучить, нет — спросить снова, кругов без ограничения;
   - «позже»/«нет» — «Хорошо, спросите ответ позже»; сессия остаётся открытой, агент работает дальше;
   - «пришли в Телеграм» — ответ уйдёт в Telegram, когда будет готов.
3. **«Скинь ответ»** — в той же сессии или при новом запуске навыка: готово — озвучить
   (подробности — в Telegram по необходимости); нет — «Ещё не готово. Подождёте?» и петля шага 2.
4. **Другая фраза, пока ответ не забран** — «Начать новый диалог или продолжить прошлый?»
   - «прошлый» — ответ или «подождёте?» (шаг 3);
   - «новый» — прошлый ответ уйдёт в Telegram, когда будет готов; начинается новая беседа (шаг 1).
5. **Ответ забран, следующий вопрос в той же сессии** — продолжение той же беседы (агент помнит
   прошлое, можно уточнять). Встречный вопрос агента («Какой жанр?») — обычный ответ; реплика на него —
   следующий вопрос той же беседы.

Telegram — только по необходимости: длинный ответ, ссылки и подробности, «пришли в Телеграм»,
выбор «новый диалог» при незабранном ответе. Короткие реплики диалога не дублируются.

Решено (2026-11-14):
- **М1.** Фраза, на которой Алиса спросила «новый или прошлый?»: при «новый» — сразу становится первым
  вопросом новой беседы, повторять не нужно; при «прошлый» — отбрасывается (иначе два вопроса подряд).
- **М2.** Новый запуск навыка, когда прошлый ответ уже забран: прошлая беседа продолжается, если с
  последней реплики прошло меньше N часов (N — настройка, по умолчанию 2); иначе — новая беседа без вопросов.
- **М3.** Запуск навыка с готовым незабранным ответом: Алиса сама говорит «Ответ на прошлый вопрос готов.
  Скинуть?»
- **М5 (основа).** Команды распознаются **интентами Яндекс Диалогов**: свои интенты навыка из
  `request.nlu.intents` плюс встроенные `YANDEX.CONFIRM`/`YANDEX.REJECT`/`YANDEX.HELP`/`YANDEX.REPEAT`
  — как в нынешнем bridge (`bridge.*`). Грамматики интентов хранятся в репозитории и описываются в
  `docs/yandex-dialogs.md`.
- **М4.** «Нет»/«позже» на «подождёте?» = «заберу голосом позже»: «Хорошо, спросите ответ позже»,
  сессия открыта, агент работает дальше. Telegram — только по явному «пришли в Телеграм» (в bridge
  «нет» = Telegram и закрытие сессии — не воспроизводим).
- **М5 (детали).**
  - Только интенты (свои + `YANDEX.*`); запасного разбора по словам нет.
  - Реплика без распознанного интента на «подождёте?»/«ещё не готово, подождёте?» — **ждём**, как в
    bridge; пустая, слэш и слишком длинная — тоже ждём. Поэтому шаг 4 («новый или прошлый?») срабатывает
    только там, где последняя озвученная реплика — не «подождёте?» (после «спросите позже», при новом
    запуске, после М3).
  - Непонятный ответ на «новый или прошлый?» — переспросить, без предела; исходная фраза хранится до
    выбора (М1).
  - «Новый диалог» работает в любой момент беседы, не только на «новый или прошлый?»: грамматика без
    `...` — совпадает только короткая фраза целиком, вопросы со словами «новый диалог» уходят агенту.
    Незабранный ответ при этом уходит в Telegram (как шаг 4).
  - Имена и префикс интентов — на этапе 2; отправная точка — `answer.get`, `dialog.new`,
    `dialog.continue`, `wait`, `later`, `telegram`.
- **М6.** Пограничные случаи: «скинь ответ» без ожидающих — «Ответов нет, задайте вопрос»; ошибка
  агента — честно «не получилось» (если ответ обещан в Telegram — сообщение об ошибке туда); перезапуск
  шлюза во время хода — «вопрос потерялся, повторите»: беседа в `state.db` цела, вопрос автоматически
  не повторяется. Точные тексты — на этапе 2.

### Хранение сессий в Hermes — проверка по коду (2026-11-14)

Только чтение checkout `3b42157858` (v0.23.1); живая проба не ставилась. Это путь API Chat

| Без заголовка (текущий bridge) | Id выводится из системного промпта + первой реплики пользователя (`_derive_chat_session_id`) → одинаковые команды bridge попадают в одну сессию `state.db`, но история из базы не подгружается | там же, `:928–936` |

### Правило, подтверждённое экспериментом

- Ход открывает `on_processing_start(event)`, закрывает `on_processing_complete(event, outcome)` —
  методы `BasePlatformAdapter` (модуль `gateway.platforms.base` целиком в `public-api.md`; в
  `adding-platform-adapters.md` хуки не описаны — только docstring). Хук приходит через 5–14 мс после итога.
- **Итог** — отправка с `reply_to == event.message_id` и `metadata["notify"] is True`
  (`_send_final_text` → `send_final_ledgered`, `gateway/platforms/base.py:4302`, `:4492`), если на ней
  нет явной `_interim_send`. Префиксы LINE `⚡ ⏳ ⏩ 💾` итог **не** отменяют (ответ агента может начинаться
  с ⏳) — ими помечаются только отправки без якоря.
- `_interim_send` и префиксы — только подсказки: многие служебные отправки идут без них.
  Правило LINE («первая отправка без метки и префикса») в этой версии озвучило бы «📬 No home channel…».
  Правило закреплено unit-тестами без Hermes: `TrackerRuleTests` в `prototypes/s1/probe_s1.py`.

Почему не VALIDATED: документированного сигнала «это итог хода» нет — `reply_to`/`notify` и
`_interim_send` («Gateway-internal», `gateway/run.py:480`) в руководстве не описаны. Риск изменения без
шима гасится тестом совместимости (этап 6).

| Текст (A) | `📬 No home channel…` (без метки, без `reply_to`) → итог (`reply_to`, `notify`) → хук `success` | верно |
| Инструмент, `minimal` (A) | `📬…` → итог → `success`; прогресса и комментария нет | верно |
| Длинный текст, стриминг включён глобально (A) | `📬…` → итог целиком → `success`; правок нет | верно |
| Два `chat_id` параллельно (A) | итоги и хуки каждого в своём чате, без перекрёстков | верно |
| Инструмент, переопределения оператора (B) | `📬…` → комментарий (`_interim_send`, `reply_to_message_id` в metadata) → `💻 Running echo hi` (**без метки и без `reply_to`**) → итог → `success` | верно |
| Пустой ответ модели (A) | `📬…` → `⚠️ Empty response … retrying (1–3/3)`, `❌ Model returned no content…` (без меток) → **итог** `⚠️ No reply: … didn't produce a reply…` → `success` | ошибка как обычный итог |
| Сбой провайдера (A, без цикла восстановления) | `📬…` → `⚠️ The AI model service kept failing…` (без метки) → **итог** `… returned a server error …` → `success` | ошибка как обычный итог |
| Сбой провайдера, 1 цикл восстановления (B) | `⏳ … retrying automatically …`, `⏳ Automatic recovery gave up…` (только префикс, metadata пуста) → `⚠️…` → итог-ошибка → `success` | ошибка как обычный итог |
| Вторая фраза в занятый чат, `interrupt` (A) | `↪ Redirected current run…` (`reply_to` = вторая фраза, без `notify`) → итог с `reply_to` **второй** фразы → хук только у первой (`success`); у второй хуков нет | **неверно**: первая закрыта «пустой» |
| Вторая фраза в занятый чат, `queue` (B) | итог первой → start/`complete` второй → итог второй с `reply_to` **первой** → `complete` первой | **неверно**: follow-up «пустой», его ответ — второй итог открывшего |

### Выводы для адаптера (этап 3)

1. `send()`: итог хода — только `reply_to == message_id` открытого хода + `notify is True` без
   `_interim_send` (префиксы не в счёт); всё остальное
   за ход — не озвучивается (кандидаты в подробности/лог — решение этапа 2). Конец хода — по хуку.

5. `display.<key>` оператора побеждает уровень `minimal`; стабильнее — `display.platforms.yandex_alice.*`

   (`asyncio.to_thread`, контекст копируется) — не проверено; у живого шлюза плагин Telegram, вероятно, уже
   загружен адаптером Telegram профиля по умолчанию.
7. **Логи**: при уровне DEBUG PTB пишет текст сообщения — в документации (этап 7) предупредить, что DEBUG
   записывает персональные данные (по коду и сырому DEBUG; файлы шлюза при DEBUG не проверялись).

### Запасной путь (только по коду, без пробы)

`ctx.register_platform_handler("telegram", factory)` (`hermes_cli/plugins_context.py:637`) — публичный API
PluginContext: при `connect()` Telegram даёт `(native PTB Application, adapter)`, адаптер «только для
чтения». Его `send()` вернул бы `SendResult` с `delivery_uncertain`, но отправка через «read-only» адаптер в
документации не разрешена, а порядок подключения адаптеров не гарантирован. Не нужен, пока standalone-путь
работает; механизм разбирается в S4 (подтверждения).

### Ограничения и что не проверено

- Не настоящий loop и `connect()` шлюза; как шлюз вызывает `connect()` адаптеров профиля по умолчанию (с
  областью или без) — не установлено, поэтому T2 в обоих вариантах (итог одинаковый).
- Настоящий Telegram, fallback-адреса `api.telegram.org` и реальный прокси не проверены (`base_url` на loopback)
  — до приёмки (этап 8).
- Медиа, темы (`thread_id`), `rich_messages` и `asyncio.to_thread` для `get()` — не проверялись.
- Обвязка опирается на `hermes_cli.plugins.discover_plugins`, `hermes_logging` и приватные карты реестра —
  только в пробе.

## Что берём из ТЗ и плана v3 (2026-11-14)

Источники — приватные ТЗ и план v3 владельца (вне репозитория). **Приоритет — решения этого документа**
(«Модель диалога»): там, где ТЗ/v3 строят всё вокруг задания (job), действует диалог.

Отклонено как противоречащее нашим решениям:
- «Нет» на предложение ждать завершает сессию — у нас сессия не закрывается (решение 2).
- Новая команда — отдельное задание, независимые команды без истории (ТЗ §2, v3 §8) — у нас одна
  беседа Hermes на сессию Алисы (решение 1).
- Привязка ответа на уточнение к заданию и вопросу — у нас уточнение просто следующий ход беседы.

Берём:
1. **Прототип S1 первым**: окончательный ответ и его принадлежность ходу — по публичному контракту,
   не по «последнему сообщению»; если контракта нет — фиксируем блокер, скрытых обходов не делаем.
2. **Подтверждения только через Telegram**, одноразовые, привязаны к владельцу и действию;
   автоподтверждения нет; «да» на «подождёте?» и «да» в диалоге — не разрешение (решение 5).
3. **`MessageEvent.allow_gateway_control=False`** — штатная защита от `/команд` с голоса
   (`gateway/platforms/event.py:121`, учитывается в `is_command()`).
4. **«Да»/«нет» — по последней озвученной реплике**: в `waiting` — выбор ожидания, реплика без интента
   там означает «ждём» и не запускает ход (М5); в `dialog` — всё уходит агенту (решение 3).
5. **Неозвученный ответ выдаётся при следующем входе**, в том числе в новой сессии и после перезапуска.
   Минимальное хранилище плагина — SQLite в каталоге данных плагина (`plugins.plugin_storage`):
   ожидающий голосовой ответ и статус доставки в Telegram. Историю по-прежнему хранит Hermes.
   Неясный исход хода или отправки автоматически не повторяется.
6. **Жизненный цикл**: импорт не открывает порт; connect/disconnect/reload оставляют один listener.
   Сценарии тестов — из `alice-voice` 0.3.2 (`e38849e`, MIT, с уведомлением об авторстве), включая
   `f9a3cf7` «listener survives a plugin reload».
7. **Cron с явным адресом доставки** (вопрос 5).
8. **Паспорт стенда**: числовые лимиты (бюджет HTTP, очередь, параллельность, хранение, дедупликация)
   до приёмки; прототипы — во временном `HERMES_HOME`, вердикт VALIDATED / PARTIAL / INVALIDATED.
9. **Переход**: старый bridge работает до приёмки, один исполнитель команд, старый контейнер после
   переключения остаётся остановленным. Caddy уже в `network_mode: host` — меняется только upstream-порт.

Не берём (избыточно для одного владельца): три машины состояний, outbox с подтверждением каждой части
Telegram-сообщения, перенос дедупликации при переключении, тесты на заполненный диск, README.ru,
SECURITY и публикацию в Marketplace. Вернуться, если понадобится.

## Что переносится из старого bridge

Стартовая точка, будет переделываться под диалог. Перенесено в `yandex-alice/protocol.py` без изменения поведения: тексты ответов, `alice_reply`, проверка тела,
`speakable`/`split_answer`, интенты и `classify_reply`, `is_control_phrase`, `RateLimiter`.
Не нужны: `ask_agent` (Chat Completions + ключи профилей), `deliver` + `sign_v2` (webhook `alice-reply`),
`_DeadlineSocket`/`_post`, свой `ThreadingHTTPServer`. `Jobs`/`Turn` заменяются кэшем по образцу LINE.

## Риски

- Код работает внутри шлюза: ошибка или зависание плагина задевают все профили и Telegram;
  перезапуск шлюза ≈ минута без Алисы.
- Внутренние модули Hermes — не API (старые пути удаляются без шимов); держаться `public-api.md`
  и прогонять `hermes plugins validate` после каждого `hermes update`.
- Локально Hermes нет: адаптер тестируется на заглушках базовых классов или на checkout сервера.
